# Design

## Context

목적과 범위는 proposal.md를 따른다. 실제 저장소에는 초기 안내용 App.tsx, TDSMobileAITProvider, Vite devtools, lint/typecheck/build 스크립트가 있다. SDK는 3.8.1, TDS 두 패키지는 2.5.1이며 도메인·저장·화면·테스트 구현은 없다. appName은 local-development이고 사용자 확인상 콘솔 등록값은 없다. 기존 파일은 모두 미커밋이므로 향후 apply에서 수정 전 백업 정책을 확인해야 한다. 이번 계획은 기존 코드와 기획서를 수정하지 않는다.

기준 문서 v1.1을 적용하되 F-05의 ‘현재 날짜 이후’와 6.1절의 ‘오늘 또는 이후’ 중 상세 규칙인 오늘 포함을 채택한다. 4.2절 목업의 ‘이번 달 기준’ 표기는 6.5절에 맞춰 ‘월 환산 예상 구독료’로 구현한다. P1 분류·검색 및 선택 메모 UI는 이번에 추가하지 않는다.

## Goals / Non-Goals

**Goals:** 계산을 순수 함수로 격리하고 저장 성공과 UI 확정을 일치시킨다. 이미 설치한 SDK/TDS를 재사용하며 세 화면의 단순한 상태와 광고 수명주기를 관리한다. 요구사항·테스트·작업의 추적 관계를 유지한다.

**Non-Goals:** 전역 상태 라이브러리, 서버, 범용 repository 계층, 무거운 날짜 라이브러리, 미리 만드는 확장 스키마, 자동 손상 복구를 도입하지 않는다. 리팩터링과 번들 최적화는 실제 문제가 확인될 때 별도 판단한다.

## Decisions

### 1. 원본 모델과 순수 계산 모듈

`types/subscription.ts`는 기획서 5.2절의 필수 필드와 schemaVersion: 1을 정의한다. id는 생성 시 고유값, createdAt/updatedAt은 ISO 시각이다. 선택 category 필드는 스키마가 허용하더라도 이번 UI에서는 편집하지 않는다. 저장 파싱 시 unknown에서 날짜·enum·금액·시각·ID 중복 등 불변 조건을 확인한다.

`domain/subscription.ts`는 폼 검증과 상태 대상 필터를, `domain/billing.ts`는 다음 결제일·D-day·환산 합계를 담당한다. 이름은 trim 후 검사하며 내부 공백을 임의 제거하지 않는다. 금액은 숫자 문자열만 받아 정수로 변환하고 JS 안전 정수 및 집계 결과의 표현 가능 범위를 검사하여 정밀도가 손실되는 값을 저장하지 않는다. 임의의 상품별 상한을 만들지 않는다. 브라우저 input 검증만 사용하는 대안은 저장 데이터에도 적용할 수 없어 배제한다.

### 2. 달력 날짜를 문자열과 구성 요소로 처리

KST 오늘은 Intl.DateTimeFormat의 Asia/Seoul 및 formatToParts로 취득한다. 날짜 문자열을 로컬 자정 Date로 암묵 파싱하지 않는다. 날짜 유효성은 실제 월 일수와 윤년 규칙으로 검사하고 D-day는 검증된 달력 날짜의 UTC 일련값 차이로 계산한다. 기기의 시간대·일광절약시간이 결과에 영향을 주지 않게 한다.

기준일이 오늘보다 미래이면 즉시 그 날짜를 반환한다. 월간은 현재 연·월에 원래 day를 대입하고 말일로 clamp한 후보를 검사하며, 후보가 오늘보다 이전이면 다음 달 후보를 다시 원래 day로 만든다. 연간은 같은 방식으로 원래 month/day에서 매년 후보를 만든다. 전 회차에 한 달/일 년을 더하는 대안은 월말 드리프트 때문에 사용하지 않는다.

현재 날짜를 함수 인자로 주입해 테스트한다. 화면에서는 초기 진입, visibilitychange로 foreground 복귀, KST 자정 도래에 날짜 상태를 갱신하고 타이머·이벤트를 해제한다. 환산은 활성의 월간·연간 원금 합계에서 구하고 표시 직전 한 번 반올림한다.

### 3. 저장 성공 후 UI 확정

`storage/repository.ts`에서 공식 `Storage.getItem/setItem`을 사용하고 키는 `subscription-radar:data:v1`로 고정한다. SDK 브라우저 mock을 개발 환경에서 사용하며 production localStorage 폴백이나 AsyncStorage는 추가하지 않는다.

상위 App의 작은 상태/훅으로 loading, ready, load-error, saving을 관리한다. ready의 확정 목록과 폼 draft를 분리한다. 변경은 확정 목록에서 candidate를 만들고 스키마 검사→직렬화→await setItem→성공 시 확정 목록 교체 순서이다. 모든 쓰기는 하나의 저장 중 잠금으로 직렬화하며 로드 전·저장 중 다른 변경을 허용하지 않는다. 낙관적 갱신 후 롤백하는 대안은 실패 시 복구 복잡성이 커 사용하지 않는다.

로드 값 없음은 신규 빈 상태이고, 읽기 실패·손상 JSON·지원하지 않는 스키마는 오류 상태이다. 부분 레코드만 걸러 저장하거나 빈 배열로 대체하지 않는다. 재시도만 제공하고 원본을 보존하며 전체 초기화 기능은 이번 범위에 넣지 않는다. 실패한 생성 재시도는 같은 draft/candidate를 사용해 중복 ID 생성을 피한다.

### 4. 세 화면과 기본 내비게이션

pages/Dashboard, SubscriptionForm, SubscriptionDetail과 실제 재사용되는 components만 만든다. TDS와 기존 provider를 유지한다. App에서 home, detail(id), form(mode,id,returnTo)의 작은 화면 상태와 브라우저 history/popstate를 연결한다. 별도 라우터 라이브러리는 세 화면에 비해 의존성이 커 추가하지 않는다. SDK의 기본 뒤로가기가 WebView 이력과 연결되는 경로를 구현 시 설치 SDK 이벤트/공식 안내로 확인하고 필요한 경우 한 곳에서 연결한다. 시스템·네이티브 이벤트를 동시에 받아 이중 pop하지 않게 한다.

홈→등록→저장/취소는 홈, 홈→상세→수정→저장/취소는 상세, 상세 삭제 성공은 홈으로 간다. 폼 뒤로가기는 미저장 draft를 폐기하고 확정 목록은 보존한다. 저장 중 이탈은 쓰기가 끝날 때까지 막아 화면 전환과 저장 확정이 엇갈리지 않게 한다. 네이티브 닫기에 의한 강제 종료 후에는 마지막 성공 저장값을 복원한다. 홈의 종료를 임의 가로채지 않는다.

전체 필터는 활성 예정 목록과 비활성 보관 목록을 별도 영역으로 보여 준다. 비활성 기록에 가짜 예정일을 만들지 않는다. 필터와 무관하게 상단 요약은 활성 전체 기준이다. 동일 날짜 정렬은 한국어 이름 비교, 동일 이름이면 ID로 고정한다. 빈 데이터·필터 없음·활성 없음·로드 실패는 각각 구분한다. 구독사 실제 해지는 별도임을 상세 상태 변경 안내에 명시한다.

### 5. 광고를 홈 수명주기에 제한

설치 SDK 선언에서 TossAds.initialize, initialize.isSupported, attachBanner와 반환값 destroy가 존재함을 확인했다. 구현 때 해당 옵션·콜백 타입과 공식 광고 안내를 확인해 사용한다. 상위에서 지원 검사 후 초기화를 한 번 수행하고 홈의 BannerAd가 DOM 마운트 후 attach한다. 해제·늦은 콜백·StrictMode 재마운트에도 인스턴스가 누적되지 않게 한다. 초기화 실패는 앱 전체 로드 실패로 전파하지 않는다.

개발에서만 공식 테스트 ID를 사용한다. 운영은 `VITE_SUBSCRIPTION_RADAR_BANNER_AD_GROUP_ID` 같은 프로젝트 환경 설정에서 주입하고 발급 전에는 미설정으로 둔다. 운영 그룹 누락·미지원·No Fill·실패는 슬롯 높이까지 제거한다. 홈 목록 하단 폭 100%로 배치하고 CTA와 간격을 둔다. 기획서의 높이·최소 앱 버전 숫자는 플랫폼 지원 검사와 실기기 결과를 우선하며 현재 정책 확인 없이 강제 버전 분기를 만들지 않는다.

### 6. 테스트와 단계별 완료 판정

Vitest로 날짜·비용·검증과 mock Storage 실패·중복 쓰기를 검증한다. UI는 React Testing Library/jsdom 등 필요한 최소 도구로 저장 실패 시 draft 보존, 삭제 취소, 필터·통계, 뒤로가기 흐름을 검증한다. 브라우저에서는 TDS와 devtools가 실제 렌더되는지 확인한다. 스크립트는 test, lint, typecheck, build로 일관되게 제공한다.

기획서 T-01~09·15~16은 날짜/집계와 날짜 변경 회귀, T-10·12는 저장·복원, T-11은 입력, T-13은 광고 예외, T-14는 삭제 취소에 대응한다. KST 시간대 경계, 30일 기준 월말, 합계 후 반올림, 손상 스키마, 중복 저장 검증을 보강한다. 코드 통과, 브라우저 통과, Android 통과, 광고 실노출, 콘솔·심사 완료는 별도로 기록한다. 필수 실기기 작업이 남으면 MVP 전체 완료·archive로 판정하지 않는다.

## Risks / Trade-offs

- [로컬 데이터 소실] → 홈 안내에 기기 의존성과 백업·동기화 없음을 표시한다.
- [금액 정밀도] → 안전 정수와 연산 결과 범위 검증으로 조용한 잘못된 계산을 막는다.
- [내비게이션 환경 차이] → 브라우저 history 회귀와 Android 시스템/토스 버튼을 각각 확인한다.
- [광고·콘솔 미발급] → 기능 구현과 외부 대기 작업을 분리하고 임시 appName 번들을 배포하지 않는다.
- [TDS 번들 크기 경고] → 현재 경고는 알려진 상태로 유지하고 초기 화면 로딩이 실제 기준을 충족하는지 브라우저·기기에서 확인한다.
- [문서의 플랫폼 정보 변동] → 구현 시 설치 SDK 타입, 출시 전 공식 체크리스트를 확인하고 검증 일시·환경을 기록한다. 이번 계획은 최신 정책 준수 판정이 아니다.

## Migration Plan

기존 앱 데이터가 없는 신규 스키마이므로 마이그레이션은 만들지 않는다. 이미 있는 SDK 설정을 유지하고 기능 모듈을 단계별 연결한다. 잘못된 버전의 저장값은 읽기 오류로 보존한다. 롤백이 필요하면 승인된 코드 기준으로 되돌리되 저장 키·데이터는 자동 제거하지 않는다. 커밋이 없는 현재 상태에서는 apply 전 사용자 변경을 보존할 백업 방식을 먼저 확인한다.

콘솔 등록 후 사용자 제공 appName으로 설정하고 개발 테스트 광고와 실제 광고를 구분하여 빌드한다. 콘솔 업로드·검수 신청·출시는 별도 요청에 따라 수행한다.

## Open Questions

- 실제 콘솔 appName, 표시명 등록 가능 여부, 광고 그룹·정산 준비 시점은 미정이다. 값의 확보는 6단계 외부 작업이며 로컬 기능 구현을 막지 않는다.
- Android 테스트 기기·토스 앱 버전·테스트 링크는 검증 단계에서 확보한다. iOS 기기가 없으면 미검증을 기록한다.
